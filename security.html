Security policy

How this app is built, what it can access, and how we handle a security report. For the technical reviewer, not just the end user.

Architecture and hosting#

CRM for Jira is built entirely on Atlassian Forge, in UI Kit (not Custom UI), so its interface is rendered by the platform itself, not by code we serve. It has no servers, databases or infrastructure of its own: it stores no data outside Atlassian, and its manifest declares no permission to make an outbound network call to anything other than Atlassian's own APIs.

Transport security, encryption, physical security and patching of the underlying platform are Atlassian's responsibility, covered by Atlassian's own compliance programme for Forge.

Data we handle#

The app handles the records your users type in. It reads a Jira work item's summary and status live when a user links one, and people's names to display. It holds no permission to create, edit, transition or comment on an issue, so it cannot write to Jira at all. Full detail on what is and is not kept is in the privacy policy.

Authentication and access control#

There is no independent login system. Every request runs as the signed-in Jira user, authenticated by Forge through their existing Jira session. We never collect, transmit or store Atlassian usernames, passwords or API tokens.

Inside the app there are no roles: anyone who can open it can read and change every record (see Permissions and access). The one exception is workspace settings, which the server only accepts from a user who holds Jira's site ADMINISTER permission, checked on every save. Access is bounded by the scopes declared in the manifest:

read:jira-workcheck that a work item exists and read its summary and status
read:jira-usershow people's names, search users for the owner and assignee pickers
storage:appthe app's own Forge key-value store

No Jira write scope is declared anywhere in the manifest. Every Jira call is made as the signed-in user (asUser), so Jira's own permissions apply.

Input handling#

Every server function validates what it receives before using it: record ids must be well-formed UUIDs, text is trimmed and length-limited, choices (stages, statuses, sources, ratings, reasons, currencies) are checked against fixed lists, numbers must be finite and non-negative, and account ids and Jira work item keys must match strict patterns. Saved-view filters are limited to a fixed set of keys. The app was reviewed against the OWASP list of common weaknesses and hardened where needed.

Reporting a vulnerability#

Email security@vudia.site with what you found, the steps to reproduce it, and which part of the app it affects. Please do not publish details until we have had a chance to fix it. For general support, use info@vudia.site.
